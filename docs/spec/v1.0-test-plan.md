# Escrow Protocol — Test Plan v1.0

**Version:** v1.0  
**Status:** Validated (aligned with Contract Spec v1.0)  
**Scope:** Validation of escrow contract logic according to Contract Spec v1.0.  
**Out of scope:** UI, gas optimization, fuzzing, upgrades, arbitration, multi-token support.

## 1. GOALS OF TEST PLAN

The goal of this test plan is to verify that:

- All state transitions defined in Contract Spec v1.0 are enforced correctly.
- No invalid transitions are possible.
- Funds are transferred exactly once and only under valid conditions.
- Access control (client/provider/owner) is enforced.
- Time-based logic (`releaseDeadline`) behaves correctly, including boundary cases.
- All final states are terminal.
- Security invariants are preserved.

## 2. TEST ENVIRONMENT ASSUMPTIONS

- `PAYMENT_TOKEN` is a standard ERC20 (USDC-like) with:
  - 6 decimals
  - no transfer fees
- Test framework provides:
  - time manipulation (warp / `increaseTime`)
  - revert expectation checks
- One contract instance deployed per test suite.
- Fresh state for each test (no state leakage).

**Actors used in tests:**

- `client`
- `provider`
- `attacker` (any other address)
- `owner` (deployer)

## 3. DEAL CREATION TESTS

### 3.1 createDeal — happy path

- `client` creates a deal with valid provider, amount, deadline

**Expected:**

- `dealId` returned
- deal stored correctly
- `status == Created`
- `createdAt` set to current timestamp
- `releaseDeadline` stored
- `metadataHash` stored
- `nextDealId` incremented
- `DealCreated` event emitted

### 3.2 createDeal — invalid provider

**Cases:**

- `provider == address(0)`
- `provider == client`

**Expected:**

- revert `InvalidProvider`

### 3.3 createDeal — invalid amount

**Case:**

- `amount == 0`

**Expected:**

- revert `InvalidAmount`

### 3.4 createDeal — invalid deadline

**Case:**

- `releaseDeadline <= block.timestamp`

**Expected:**

- revert `InvalidDeadline`

### 3.5 createDeal — multiple deals

- `client` creates multiple deals

**Expected:**

- `dealId` increments starting from 1
- deals stored independently

## 4. FUNDING TESTS

### 4.1 fundDeal — happy path

- `client` approves `PAYMENT_TOKEN`
- `client` calls `fundDeal`

**Expected:**

- token transferred to contract
- `deal.status == Funded`
- `DealFunded` event emitted

### 4.2 fundDeal — missing allowance

- `client` does not approve `PAYMENT_TOKEN`

**Expected:**

- revert (ERC20 `transferFrom` failure)

### 4.3 fundDeal — insufficient balance

- `client` approves but balance < amount

**Expected:**

- revert (ERC20 `transferFrom` failure)

### 4.4 fundDeal — non-client caller

- `provider` or `attacker` calls `fundDeal`

**Expected:**

- revert `NotClient`

### 4.5 fundDeal — wrong status

**Cases:**

- `fundDeal` on `Canceled` deal
- `fundDeal` on `Funded` deal

**Expected:**

- revert `WrongStatus(Created, actual)`

### 4.6 fundDeal — deal does not exist

**Case:**

- `fundDeal` with non-existent `dealId`

**Expected:**

- revert `DealNotFound`

## 10. FINAL STATE INVARIANTS

For each final state (`Released`, `Refunded`, `Canceled`):

- No function call can change status further.
- No token transfers can occur.
- Any attempt to post-action reverts with `InvalidStatus` or `WrongStatus`.

## 12. SECURITY TESTS

### 12.1 Reentrancy protection

### 12.2 Double-spend protection

- ensure `PAYMENT_TOKEN` is transferred exactly once per deal

### 12.3 Unauthorized access

**Expected:**

- all revert correctly
